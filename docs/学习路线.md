# 从复习 Agent 迁移到电商客服

这里把原系统里的 Agent 思路换成一个具体业务：**查到事实，再回答；有写入动作，先确认。** 不需要先研究大型多 Agent 框架。

后端入口在 `backend/app/main.py`，它只负责启动资源、注册异常处理和装配路由。请求模型与同源校验在 `api/`，聊天 SSE 的连接生命周期在 `api/chat.py`，Agent 事件保存和取消恢复在 `services/chat_stream.py`。后面的章节再进入 Agent 和业务层。

## 第一步：分清两类事实

打开 `backend/app/store.py`：

- 商品价格、库存、订单、物流是结构化数据，必须走数据库/业务 API。
- 退货政策、保修说明是文本知识，适合切分后向量检索。

例如“耳机多少钱，能退吗？”可能同时需要 `search_products` 和 `search_knowledge`。模型负责选择工具和组织回答；价格不能只从训练记忆里猜。

## 第二步：理解 MCP 的位置

打开 `mcp_server.py`，只有四个工具：

| 工具 | 输入 | 输出 | 是否写数据 |
| --- | --- | --- | --- |
| `search_products` | 商品问题 | 价格、库存、规格 | 否 |
| `lookup_orders` | 可选订单号 | 当前客户订单 | 否 |
| `search_knowledge` | 政策问题 | 检索片段、来源 | 否 |
| `prepare_after_sales` | 订单号、原因 | 售后草稿 | 只写草稿 |

MCP 是把这些能力提供给 Agent 的协议，并不是大模型，也不是向量数据库。这里用 `stdio`，主服务启动工具子进程，不额外占用一个公网端口。

`agent.py` 在一次回答期间维持同一个 MCP 会话，`load_mcp_tools()` 将 MCP 工具转成 LangChain 可调用的工具。换成 HTTP MCP 服务是传输层的变化，业务校验仍然要保留。

注意订单工具的参数里**没有 customer_id**。客户范围由 FastAPI 验证浏览器身份后，通过子进程环境注入。提示词可以提醒模型不要越权，真正的权限必须由工具后面的代码检查。

## 第三步：看 Agent 循环

在 `agent.py` 找到：

```python
graph = create_agent(
    model=model(),
    tools=tools,
    system_prompt=SYSTEM_PROMPT,
    middleware=[ToolRecoveryMiddleware()],
    checkpointer=checkpointer,
)
```

用“SG20260001 不合适，我想申请退货”跟踪：

1. 用户消息传给模型。
2. 模型生成 tool_calls，查询订单、检索政策。
3. 工具返回 ToolMessage，模型读取结果。
4. 符合条件时，调用 `prepare_after_sales` 生成草稿。
5. 模型输出解释，页面显示确认按钮。
6. 用户点击，FastAPI 直接调用业务层核验并登记工单。

第 2～4 步可以循环多次。真实模型自己决定顺序，系统提示词指导，业务层校验兜底。规则演示模型用可读的条件分支复现常见路径，所以自然语言理解能力有限。

## 第四步：走一遍 RAG

打开 `knowledge.py`：

```text
读取 knowledge/*.md
  → RecursiveCharacterTextSplitter（380 字符，重叠 60）
  → Embeddings.embed_documents
  → Milvus Lite 保存 text/source/chunk/vector

用户问题
  → Embeddings.embed_query
  → Milvus COSINE 检索
  → 带文件名的片段送回模型
  → 回答 + 页面引用
```

向量解决“哪些文字可能相关”，不代表匹配结果一定正确。默认本地字符向量主要体现词面相似度；实际语义搜索需要切换真正的 Embedding 服务，并用典型问题评估召回。

为什么 MCP 不直接再打开 Milvus 文件？因为文件式 Milvus Lite 不适合不同进程竞争读写。工具子进程携带随机内部令牌，请求主进程的 loopback 检索接口，由主进程唯一管理 Milvus 客户端；Nginx 不代理内部路径。

修改一个 Markdown 文件后重新提问，观察内容指纹变化和重建。只有文档、Embedding 模式/模型/地址变化才会重建，不会每轮重新入库。

## 第五步：把“记忆”拆成两部分

`backend/data/`（Docker 为 `runtime/data/`）包含：

| 文件 | 内容 |
| --- | --- |
| `commerce.sqlite3` | 商品、订单、匿名访客、可展示消息、售后申请 |
| `checkpoints.sqlite3` | LangGraph 状态，含 HumanMessage、AIMessage、ToolMessage |
| `knowledge.db` | Milvus Lite 向量库 |
| `knowledge.json` | 入库指纹和切片统计 |

聊天页面读取的是业务消息表。Agent 下一轮需要的完整工具上下文来自 Checkpointer，两者用途不同。只存页面文字，恢复后模型未必知道之前工具做了什么；只存 Checkpointer，页面又缺少方便查询的聊天记录。

`thread_id = 访客 + 演示客户 + 会话`，可防止不同浏览器、不同演示身份串用 Agent 状态。Cookie 丢失后会被视为新访客，没有跨设备同步登录功能。

停止流式生成可能让历史 AIMessage 带着 tool_calls 而缺少 ToolMessage。`middleware.py` 会补错误结果，保证消息序列合法，再让模型继续处理当前问题。

## 第六步：理解流式界面

后端的 `StreamingResponse` 使用 SSE 格式，但请求是携带 JSON 的 `POST fetch`，并非浏览器 `EventSource`：

| 事件 | 页面行为 |
| --- | --- |
| `start` | 确认会话 ID |
| `token` | 追加文字 |
| `reset` | 清除工具阶段的临时文字，防止混入最终回答 |
| `state` | 更新工具过程与引用 |
| `done` | 使用已保存的最终答案 |
| `error` | 展示中文错误和已保存的中断回答 |

不要用 `split('\n')` 直接解析每个网络包：中文 UTF-8 字节和事件边界都可能跨包。`frontend/src/stream.js` 用流式 TextDecoder 累积完整事件。

## 可以自行练习的三个改动

1. **新增优惠券查询**：SQLite 加优惠券表，增加 `lookup_coupons` MCP 工具，修改 Prompt，让模型回答优惠适用条件。
2. **增加人工转接工单**：仍采用“草稿 → 页面确认”的模式，先不要直接把工具接到真实工单系统。
3. **评估 RAG**：准备 10 个问题，记录是否召回正确文件；对比字符向量与真实 Embedding，调整切片大小和 Top K。

每次新增业务，优先写清楚：数据从哪里查、谁有权限、什么动作需要确认、失败时怎么告诉用户。再决定工具和提示词，学习过程会更清楚。
